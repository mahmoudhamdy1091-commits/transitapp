## ٢. التصميم المقترح (من غير كود)
1. **`apiDelete` ياخد `audit` كمان:** `apiDelete(table, match, { allowEmpty = false, audit = true } = {})` — النداءات اللي بتكتب audit تفصيلي بنفسها
   تقول `audit: false` عشان مايبقاش سطرين لنفس المسح. (التغيير الوحيد في apiDelete؛ الافتراضي زي ما هو.)
2. **المواضع الأربعة يستخدموا apiDelete (strict) بدل fetch مباشر:**
   - `deleteJEEntry`: `apiDelete('journal_entries', { entry_no, system_type }, { audit: false })` ⇒ 0 ⇒ رسالة ZERO_ROWS_MSG، والـaudit التفصيلي
     الموجود + «✅ تم» بعد النجاح بس.
   - `submitJE` (تعديل): `apiDelete(…, { audit: false })` قبل الإدراج ⇒ 0 ⇒ يوقف **قبل** ما يدرج («فشل حذف القيد القديم: …»). الـaudit UPDATE
     الموجود (oldLinesSnapshot) زي ما هو.
   - `fixUnbalancedEntries`: `apiDelete(…)` (audit افتراضي — سجل للمسح) ⇒ 0 ⇒ القيد ده `failed++` و**من غير إعادة توليد**.
   - `_cleanupDeleteDraft`: `apiDelete(tbl, { id }, { audit: false })` ⇒ 0 ⇒ رسالة، والـaudit الخاص بعد النجاح بس. ⚠️ `CLEANUP_TABLES` =
     payments/expenses/collections/partner_payouts (cleanup.js:9) — **الأربعة في `protectedTables`** ⇒ apiDelete هيضيف فحص `can('delete')`
     (admin بس) اللي مكانش موجود هنا. متّسق مع قاعدة المسح في الشاشة، والأداة بتتشغّل من الـconsole (`inspectFileDraftLeftovers('BOX-126')`
     — cleanup.js:12) ⇒ مقبول، بس يتقال.
   - `postDoubleEntry` (engine:1120) **مايتلمسش**.
3. **الاختبار:** نفس harness N-39 (HEAD ↔ الجديد، fetch وهمي): المسار الطبيعي = HEAD بعد تطبيع `select=id`؛ و[] ⇒ رسالة ومن غير
   إعادة توليد/إدراج/audit؛ و403/500 ⇒ رسالة. + فحص حي بحاجز وهمي على قيد مش موجود.
