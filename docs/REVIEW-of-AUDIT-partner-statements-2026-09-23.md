**٤) قرار ت١ (2026-09-20):** الصيغة `actualContribution + profitShare − withdrawn` صحيحة للجميع بشرط إن التوجيه يبقى صح. دفعة من بنك الشركة: صفر أثر على حساب الشريك. دفعة من جيب الشريك (دائم أو خارجي): حسابه يُدان بيها. توزيع الربح عند الإقفال: حسابه يُدان بنصيبه.

**٥) المفاهيم**

| الاسم في الكود | المعنى | استخدامه |
|---|---|---|
| `fairShare` = fullCost × الحصة | نصيبه من التكلفة | إداري |
| `actualContribution` = capitalPaid + expPaid (للخزينة: بالمتبقي) | اللي دفعه فعلًا | |
| `fairShareDiff` = الفعلي − العادل | «فرق التمويل» | تسوية بين الشركاء، **مش بيدخل أي سقف صرف** |
| `profitShare` = الربح × الحصة | | |
| `netDue` = fairShareDiff + profitShare | صافي التسوية | مجموعه = ربح الملف لو فيه خزينة |
| `grossEntitlement` = actual + profitShare − withdrawn | المستحق على الورق | **مش بيطرح التحصيلات الممسوكة** |
| `cashAvailable` = collectedCash × الحصة − withdrawn − held | سقف النقد | |
| `payableNow` | max(0, gross) للمقفول، وmax(0, min(gross, cash)) للمفتوح | |

من 2026-09-23 الدالة بترجّع `null` للدائم (والخزينة) في `actualContribution / fairShareDiff / netDue / grossEntitlement / payableNow`. السبب إن الشريك الدائم مالوش مطالبة رأس مال، والأرقام الخام كانت بتصوّره مدين أو دائن غلط. الحقول اللي فضلت أرقام حقيقية: `capitalPaid، expPaid، collectionsHeld، withdrawnViaPayout، netJE2400، fairShare، profitShare، cashAvailable`.

**٧) م٦**
- `post_file_profit_all`: SQL ذرّي، للمدير بس، للملف المقفول بس، ومش بيتكرر (idempotent).
  - بيرحّل نصيب الدائم لحسابه.
  - بيوزّع نصيب الخزينة على الملّاك، ويستبعد المالك اللي هو أصلًا شريك مباشر على نفس الملف (إصلاح الازدواج 09-23).
  - بيتخطّى الخارجي.
- `checkPayoutCap` بقت تقرأ `profit_postings`.
- **صفر ترحيل** (`profit_postings` = 0 صف). المالك قال صراحة: «الترحيل هيتم في الآخر بعد إتمام كامل الخطة» لحد ما الكشف يتطابق.

**٨) حالات السجلات**
- `draft` = مستني موافقة، ومالوش قيد.
- `posted` = له قيد.
- `pending_edit` و`pending_void` = كان مرحّل، وطلب تعديل أو إلغاء قيد المراجعة، وقيده لسه قائم.
- **`cancelled` = اترفض قبل ما يحصل، فمفيش أي أثر محاسبي.**

الفرق مهم لأن أي كود يطرح `voided` بس هيعدّ الـcancelled كأنها حقيقية، وأي كود يتجاهل قيود العكس هيعدّ الـvoided مرتين.

**§٦-ج القاموس.** صحيح في أغلبه، مع 3 تصحيحات محاسبية:
- **«الرصيد (لك / عليك)» للخارجي = `grossEntitlement`: غلط في حالة واحدة.** القاموس نفسه بيعرّف «استلم» = `withdrawnViaPayout + collectionsHeld`، فـ«الرصيد = دفع + ربح − استلم» = gross − held، **مش** gross. `grossEntitlement` ما بيطرحش التحصيلات اللي الشريك ماسكها (G-31). والحالة كامنة النهارده (صفر تحصيل في إيد شريك).
  - **التعريف الصح:** `actualContribution + profitShare − withdrawnViaPayout − collectionsHeld`.
  - ولازم قاعدة لـ«تأكيد استلام»: يحوّل الممسوك لمسحوب **بدل** ما يضيف عليه، عشان مايتطرحش مرتين في `cashAvailable`.
- **الملف المفتوح:** الرقم ده «رصيد حسابه في الشراكة» (جزء منه رأس مال محبوس في مخزون)، **مش** مبلغ مستحق الدفع. الصياغة لازم تفرّق: «رصيدك» غير «قابل للصرف».
- **«قابل للصرف الآن» = `payableNow` / `checkPayoutCap`:** دول **مش نفس الرقم**.
  - في TM: `checkPayoutCap` = المرحّل − المسحوب منه، و`payableNow` = null.
  - في BOX بعد أي ترحيل: `checkPayoutCap` = payableNow + المرحّل − المسودات.
  - فالمصدر الوحيد لازم يبقى `checkPayoutCap`.
- **«دفع» = `actualContribution`:** للدائم null. الكلمة الصحيحة له «دفع من جيبه» = `capitalPaid + expPaid` (وده صح بس لما التوجيه يبقى صح، شوف N-01).

**§٧ الأسئلة.** كلها قرارات بيزنس فعلًا ما عدا س٩ وس١٠ (معيار شكل)، وس١٢ (محسوم في ت١ بصيغته الحالية). **الأسئلة الناقصة:**
